# AGENTS.md — `hivemind-homeassistant`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

A Home Assistant custom integration (`domain: hivemind`, install via HACS or
manually into `custom_components/`) that connects a Home Assistant instance to
an OpenVoiceOS device over the HiveMind protocol and exposes it as HA entities
— a connection sensor, control buttons/switches, and, depending on
`device_type`, a `media_player`, a `notify` service, status sensors, and a
listening-mode selector. It does more than relay voice commands: it injects
low-level bus messages to control audio playback, volume, microphone, sleep/
wake, and system power, so the connecting HiveMind client key needs admin
privileges and the message-type allowlist documented in the README. Part of
the [HiveMind](https://github.com/JarbasHiveMind) ecosystem — the hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); this
integration talks to it via `hivemind_bus_client`. Related repos:
[hivemind-player-protocol](https://github.com/HiveMindInsiders/hivemind-player-protocol),
[ovos-skill-music-assistant](https://github.com/HiveMindInsiders/ovos-skill-music-assistant),
[ovos-media-plugin-mass](https://github.com/HiveMindInsiders/ovos-media-plugin-mass).

## Layout / build / test

- Integration code lives in `custom_components/hivemind/` (config flow,
  platforms: `binary_sensor`, `button`, `media_player`, `notify`, `select`,
  `sensor`, `switch`, shared `entity.py`/`const.py`). Tests live in `tests/`
  (do not create a second test directory); `tests/e2e/` is a separate,
  real-hub tier excluded from the default run via `pytest.ini`'s
  `norecursedirs`.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -r requirements_test.txt --prerelease=allow`
- Tier 1 (no network, default): `python3 -m pytest tests -q`. Uses
  `pytest-homeassistant-custom-component` plus the integration's own runtime
  deps (`hivemind_bus_client`, `ovos-bus-client`, `ovos-utils`,
  `json_database`) so the component actually imports during tests.
- Tier 2 (`tests/e2e/`, needs a real loopback `hivemind-core` hub): install
  `requirements_test_e2e.txt` with `--pre` (it pulls `hivescope`, still
  prerelease, pinned to a loopback-whitelist branch) and run
  `python3 -m pytest tests/e2e -o norecursedirs= -q`. This is what CI's `E2E`
  workflow does.
- Lint with `ruff check custom_components tests` (CI's `Lint` workflow).
  `Hassfest` and `HACS Validation` CI jobs check the manifest and HACS
  metadata — keep `manifest.json` and `hacs.json` valid.
- `uv`, never `pip`, for local dev installs. If latest prereleases fail to
  install or resolve, that is a bug to FIX at the source, not to work around
  with a pin downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's
  stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`
  otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries, at
  the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT human-reviewed.
  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a comment
  instead; on your own PRs, edit the body rather than piling on comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and standalone:
  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.
- **Keeping this AGENTS.md current is a quality gate.** Any PR that changes this
  repo's conventions, build/test commands, dependencies, entry points, or
  observable behavior updates AGENTS.md in the same PR. A stale AGENTS.md is a
  review-blocking defect, the same tier as a failing test.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why). The manifest
  already pins `hivemind_bus_client>=0.4.3` this way.
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- HA integration requirements live in `custom_components/hivemind/manifest.json`
  (installed by Home Assistant itself on load); test-only deps live in
  `requirements_test.txt` / `requirements_test_e2e.txt`. Never install from
  git for a runtime dependency — depend on a published PyPI alpha; the
  `hivescope` git pin in `requirements_test_e2e.txt` is a test-only, temporary
  exception (pinned to a fix branch until the fix ships to PyPI) and should be
  dropped once that fix is released.
- **This repo is MIT-licensed** (`LICENSE`), not Apache-2.0 like most of the
  HiveMind ecosystem — do not change the license without the maintainer's
  explicit say-so. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- This is a SATELLITE/APP: an end-user Home Assistant integration built on top
  of `hivemind_bus_client`, not a transport or a client library itself — wire
  protocol changes belong upstream in `hivemind_bus_client`, not here.
- The HiveMind client key this integration uses needs **admin** privileges and
  the specific message-type allowlist documented in the README's "Permissions
  Required" section — any new bus message this integration sends must be added
  to that list, in the same PR, or the change silently breaks for users who
  scoped their key correctly.
- Bad credentials or an unreachable hub must fail fast and visibly: the config
  flow already checks the connection before saving and surfaces
  `cannot_connect` / `invalid_auth`, not a silent failure — preserve that on
  any config-flow change.
- Named/config entries imply a real remote client: `host`, `access_key`,
  `password`, and TLS handling (`allow_self_signed`) are per-instance secrets
  set through the HA config flow UI. Never hardcode a key, host, or password
  in code, tests, or docs; test fixtures use `tests/fake_bus.py`.
- Keep `README.md` and `docs/` truthful to the actual config-flow fields,
  `device_type` platform matrix, and permissions list — this is what a real
  user follows to connect Home Assistant to a hub.
